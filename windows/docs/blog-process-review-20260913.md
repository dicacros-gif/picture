# Blog 전체 프로세스 재검토 및 개선 계획

작성일: 2026-09-13

이 문서는 이번 인터뷰에서 확정한 운영 기준, 코드에서 확인한 문제와 수정 방향, 통합 검증 항목을 정리합니다. 테스트 실행 결과와 실행 파일 배포 결과, 실제 네이버 발행 결과는 최종 검증 후 별도로 기록합니다.

## 1. 인터뷰에서 확정한 운영 기준

| 항목 | 확정한 동작 |
| --- | --- |
| 기본 원고 구성 | 전체 본문 4,000자 이상, 8개 구역을 유지합니다. 기본은 자연스러운 구성입니다. |
| 구역별 분량과 키워드 밀도 | 기본 모드에서는 각 구역 650자와 주제어 밀도 하한을 강제하지 않습니다. 필요한 설명의 길이에 따라 구역별 분량을 달리합니다. |
| 기존 문체 | 현재 기본 말투·후킹·제목과 해시태그 규칙을 유지합니다. 사용자가 편집하여 저장한 프롬프트는 추가 지침으로 적용합니다. |
| 엄격한 분량 옵션 | 필요할 때 구역별 분량·밀도를 검사하는 모드를 선택할 수 있습니다. |
| 이미지 실패 복구 | 실패한 이미지마다 추가 생성 최대 2회를 기본값으로 합니다. 검수를 통과한 다른 이미지는 유지합니다. |
| 이미지 구성 | 기본 이미지 6장에 Google 참고사진을 더합니다. Google 기본 요청 수는 4장, 설정 가능한 최대 수는 10장입니다. 최종 이미지는 최대 16장입니다. |
| Google 검색 | CLI가 글의 의도에 맞는 영어 검색어를 만들고 영어 원문에서 사용 조건을 확인합니다. |
| Google 사용 조건 | 원문에서 확인한 CC0·공개 도메인 등 출처 표시 의무가 없는 재사용 허용 조건을 적용합니다. |
| Google 사진 설명 | 원본의 글자 없음 검수 후 사진 위 별도 영역에 공백 포함 10자 이내 한글 핵심 설명을 넣고, 완성 이미지의 문자를 다시 검사합니다. |
| 설정 변경 시점 | 저장한 프롬프트·모델·단계·이미지 옵션은 다음 새 글부터 적용합니다. 확정한 주제를 복구하는 동안에는 그 글의 설정을 유지합니다. |
| 반복 간격 | 1~6시간을 선택합니다. 대기 중 바꾸면 다음 예약 시간을 다시 계산합니다. |
| 실패한 주제 | 확정한 주제를 유지하고 원고·이미지·편집기 단계별로 복구합니다. 같은 원고가 이미 제출됐는지는 발행 영수증으로 먼저 확인합니다. |

Google 요청 수는 확보할 후보 수입니다. 라이선스·원본 문자·본문 관련성·최종 캡션 검사를 통과한 사진만 추가하므로 실제 추가 수는 설정값보다 적을 수 있습니다. 생성 이미지가 부족한 경우에는 허용 조건과 검수를 통과한 참고사진을 기본 6장 구성의 부족분에 사용할 수 있습니다. 첫 이미지의 생성 표지 조건은 유지합니다.

## 2. 전체 실행 흐름

1. 저장된 설정과 선택 프롬프트를 읽습니다. 자동 시작 설정과 현재 작업 상태를 확인합니다.
2. 미완료 주제가 있으면 해당 주제의 저장된 설정과 진행 자료를 복원합니다. 이미 준비된 원고는 다시 만들지 않습니다.
3. 새 글을 시작할 때 최신 설정 스냅샷을 만들고 CLI 연결 상태를 확인합니다.
4. 실시간 검색어와 연관 검색어를 수집합니다. 차단어·발행 이력·중복 조건을 먼저 적용하고 연관어가 풍부한 후보를 우선 검토합니다.
5. CLI가 후보 묶음을 비교하여 검색 의도와 글의 범위를 정합니다. 선정한 원래 검색어와 실제 글 주제를 각각 보존합니다.
6. 사용자 프롬프트와 단계별 역할·모델에 따라 작성, 교차 검수, 사실·최신 정보 보강, 문체 다듬기를 수행합니다.
7. 전체 길이·8개 구역·연결 문장·소제목 연관어·중복 문장·어미 반복·공개 금지 표현을 검사하고 필요한 부분을 보완합니다.
8. 생성 이미지 후보를 만들고 검수합니다. 실패한 파일만 정해진 횟수 안에서 다시 생성합니다.
9. Google 참고사진은 영어 검색·원문 조건 확인·원본 무문자 검수·한글 캡션 추가·최종 이미지 재검수를 순서대로 수행합니다.
10. 승인된 글과 이미지를 네이버 편집기에 넣고 선택한 완료 동작을 수행합니다.
11. 발행 모드에서는 게시 URL을 먼저 확인해 영수증에 기록하고, 게시된 본문·사진·강조 서식을 확인합니다.
12. 확인된 발행 이력과 소비 키워드를 저장합니다. 내용 확인까지 완료한 회차는 산출물을 정리하고 다음 예약을 기다립니다.

LLM 호출은 기존 CLI 경로를 사용합니다. 공개 원고에는 도구의 작업 설명이나 내부 검수 자료를 넣지 않습니다.

## 3. 이번 검토에서 확인한 문제와 복구 구조

### 3.1 편집기 진입 실패와 실제 제출 실패를 구분

기존에는 브라우저 작업을 시작하기 전에 `publication_started`를 표시했습니다. 로그인이나 편집기 진입에 실패해 최종 발행을 누르지 않았어도 다음 회차가 같은 표시를 보고 멈췄습니다. 임시저장이나 입력만 수행하다 실패한 경우에도 같은 문제가 발생할 수 있었습니다.

변경 경로는 준비한 원고를 `prepared_article`로 보존하고 진행 단계를 기록합니다. 재실행 시 `publication_receipt_for()`로 해당 글의 실제 제출 기록부터 읽습니다.

| 복원한 상태 | 처리 |
| --- | --- |
| 원고 준비 도중 | 저장된 작업 폴더와 검수 결과로 같은 주제의 준비를 이어갑니다. |
| 준비 완료, 최종 제출 영수증 없음 | 준비된 같은 원고로 편집기 입력을 다시 시작합니다. |
| 게시 성공 영수증 있음 | 재생성·재발행 없이 이력 기록과 후처리를 이어갑니다. |
| 제출했으나 결과 불확실 | 제출 상태와 자료를 보존합니다. 같은 글의 최종 발행 버튼을 다시 누르지 않습니다. |
| 임시저장·입력만 작업 실패 | 자동 발행 영수증과 구분하여 준비된 원고의 편집 작업을 복구합니다. |

주요 코드: `blog_controls.py`의 `_cli_automation_cycle`, `_complete_selected_topic`, `_pending_publication_receipt`, `_record_cli_publication`; `naver_automation.py`의 `publication_receipt_for`.

### 3.2 준비 완료 원고의 제목 중복을 같은 주제 안에서 수정

기존에는 원고가 완성된 뒤 제목 중복이 발견되면 그 폴더를 재개 경로로 저장했지만, 워크플로가 준비 완료 폴더의 재개 자체를 거부했습니다.

중복된 제목과 최근 발행 제목을 `revision_feedback`으로 전달합니다. 주제는 유지하면서 제목과 관점을 고치고, 기존 결과를 그대로 승인하는 캐시 재사용을 제한합니다. 준비 완료 폴더도 명시적인 수정 피드백이 있으면 수정 경로로 다시 열 수 있습니다.

### 3.3 게시 성공과 게시 내용 확인 결과를 분리

게시 URL을 확인한 즉시 `published=True`를 먼저 저장합니다. 그다음 제목, 본문 8개 구역, 이미지 수·위치·식별 정보, 굵은 글씨와 색상 표현을 확인합니다.

본문 확인이 끝나지 않아도 이미 성공한 발행을 실패로 되돌리지 않습니다. `content_verified=False`와 확인하지 못한 항목을 기록하고, 검토에 필요한 원고와 이미지를 보존합니다. 이 상태에서 같은 글을 자동으로 재발행하지 않습니다.

정상적인 산출물 삭제 조건은 게시 성공, 발행 이력 저장, 게시 내용 확인 완료입니다. 오래된 영수증에 내용 확인 정보가 없으면 확인되지 않은 상태로 구분합니다.

## 4. 글쓰기 품질과 사용자 프롬프트

### 4.1 자연스러운 구성 모드

기본값은 `editorial_mode="natural"`입니다. 전체 4,000자 이상과 8개 구역은 유지하고 각 구역을 똑같이 650자 이상으로 늘리지 않습니다. 거의 내용이 없는 구역은 보완 대상으로 잡지만 길이를 맞추기 위한 상투적인 문장 추가를 지시하지 않습니다.

주제어 밀도의 하한을 해제합니다. 밀도를 맞추려고 같은 키워드를 반복하지 않고 과도한 반복만 줄입니다. 연결 문장, 서로 다른 소제목 연관어, 독자가 실제로 필요한 조건·절차 설명은 계속 검사합니다.

엄격한 모드 `editorial_mode="strict"`에서는 기존 구역별 분량과 밀도 검사 옵션을 사용합니다.

### 4.2 문체와 역할 유지

- 사용자가 저장한 프롬프트를 선택한 상태로 유지하고, 프롬프트에 추가한 지침도 저장합니다.
- 어미와 질문형 후킹은 현재 사용자 프롬프트의 규칙을 따릅니다. 같은 어미가 반복되는 부분과 여러 구역에 되풀이되는 상투적인 문장을 수정 대상으로 잡습니다.
- Antigravity의 사실·최신 정보 보강 역할은 확인 자료를 바탕으로 내용을 보강하는 역할로 유지합니다.
- 마지막 문체 다듬기는 사실을 바꾸거나 직접 겪지 않은 경험을 만들어 넣는 용도로 사용하지 않습니다.
- 공개 제목·본문에는 출처 목록, URL, 도구가 확인했다는 설명, 검수 경과를 넣지 않습니다. 사실 확인 자료는 내부 기록으로 보존합니다.

기계적 검사와 부분 수정은 사용자 프롬프트가 지정한 문체를 보완하기 위한 과정입니다. 확인되지 않은 수치나 새로운 사실을 코드의 길이 보충 처리로 만들어 넣지 않습니다.

## 5. 이미지 생성과 Google 참고사진

### 5.1 생성 이미지 재시도

Antigravity와 ChatGPT의 기존 이미지 생성 분담과 후보 8장 생성 흐름을 유지합니다. `image_retry_limit`의 기본값은 2이며 화면의 설정 범위는 1~3입니다. 값은 최초 생성 이후의 추가 생성 횟수를 뜻합니다.

생성·시각 검수·중복 판정에서 실패한 위치만 다시 생성합니다. 호출 전에 위치별 생성 시도 수를 기록하여 중지·재실행으로 재시도 한도가 초기화되지 않게 합니다. 이미 승인된 서로 다른 이미지의 파일과 검수 결과는 보존합니다.

재개 직후 또는 원고 단계에서 멈춰도 이전 후보와 누적 횟수를 보존합니다. 이미지 단계에서는 해당 위치만 갱신하므로 앞쪽 파일 처리 도중 중지해도 뒤쪽 승인본이 사라지지 않습니다. `image_context_sha256`으로 본문·이미지 프롬프트·표지 문구·이미지 규칙을 묶어, 원고를 바꾼 후에는 이전 문맥의 승인을 그대로 사용하지 않습니다.

같은 폴더에서 원고를 수정한 경우에는 수정된 본문과 이미지의 관계를 다시 확인합니다. 첫 이미지의 한글 후킹, 본문 이미지의 실사 표현, 왜곡·문자·품질 검사는 유지합니다.

### 5.2 Google 참고사진의 확정 파이프라인

Google 검색 결과 순위나 화면 캡처 자체를 재사용 허가로 판단하지 않습니다. 인터뷰에서 확정한 전체 경로는 다음과 같습니다.

1. 확정된 주제와 검색 의도를 CLI에 전달하여 사진 검색에 적합한 영어 검색어를 만듭니다.
2. 영어 검색어로 후보를 찾고 영어 원문을 엽니다. 검색 화면의 언어 설정만으로 원문 언어를 확인했다고 처리하지 않습니다.
3. 해당 이미지의 원문·라이선스 페이지에서 CC0 또는 공개 도메인과 상업적 사용·변형 허용·표시 의무 조건을 확인합니다.
4. 원본 사진의 문자·워터마크 없음, 해상도, 왜곡, 본문 관련성을 CLI 시각 검수로 확인합니다. 검수를 위해 원래 있던 글자를 덮거나 지우지 않습니다.
5. 해당 구역의 핵심 설명을 한글을 포함한 공백 포함 10자 이내 한 줄로 만듭니다. 새 수치나 주장을 추가하지 않습니다.
6. 사진 위 별도의 짙은 배경 영역에 읽기 쉬운 고딕체로 설명을 넣습니다. 원래 사진 영역을 덮거나 잘라내지 않습니다.
7. 최종 업로드 사본을 다시 검사합니다. 지정한 설명이 정확하게 읽히고 다른 문자가 없는지 OCR 성격의 시각 검수를 수행합니다.
8. 라이선스·원본·최종 사본 검수를 모두 통과하고 다른 이미지와 중복되지 않은 사진만 채택합니다.

`google_reference_count` 기본값은 4이고 설정 범위는 1~10입니다. Google 사용 여부는 별도 옵션입니다. 기본 이미지 6장과 추가 참고사진을 합한 상한은 16장입니다.

### 5.3 캡션 파일 규약

`image_delivery.clean_export(..., caption="핵심 설명")`이 상단 설명 영역을 만듭니다. 캡션은 한글 음절을 포함해야 하며 줄바꿈·제어 문자·URL을 허용하지 않습니다. 표지 후킹용 `headline`과 동시에 적용하지 않습니다.

주요 결과 필드는 다음과 같습니다.

| 필드 | 의미 |
| --- | --- |
| `caption_text` | 실제 적용한 설명 |
| `caption_applied` | 설명 적용 여부 |
| `caption_placement` | `top` |
| `caption_layout` | `separate_band` |
| `caption_band_height` | 원사진 위에 추가한 영역의 높이 |
| `original_text_free` | 원본 무문자 검수 승인 여부. 워크플로에서 기록합니다. |
| `source_reviews` | 캡션 추가 전 원본의 시각 검수 기록 |
| `reviews` | 설명이 포함된 최종 사본의 정확성·가독성·추가 문자 검수 기록 |

업로드 사본은 기존 EXIF 방향 처리를 거친 JPEG로 만듭니다. 원본을 덮어쓰지 않고 기존의 업로드 메타데이터 정리 규칙을 유지합니다. 생성·수집 경로와 검수 자료는 내부 작업 기록으로 구분합니다.

## 6. 설정 저장과 예약

`automation_config_snapshot(settings, fallback)`은 Tk 위젯에 접근하지 않고 저장된 일반 데이터에서 실행 설정을 만듭니다. 선택 프롬프트, 단계별 CLI·역할·모델, 검수 방식, 완료 동작, 이미지 옵션, 블로그 ID와 중복 기준을 한 글의 설정으로 묶습니다.

새 주제를 확정할 때 스냅샷을 미완료 작업 자료에 함께 저장합니다. 진행 중 설정을 바꿔도 그 글의 복구는 저장된 설정으로 이어가고 다음 새 글에 변경값을 적용합니다.

간격은 예약 정책이므로 대기 중에도 바꿀 수 있습니다. 대기 루프는 최대 1초 단위로 중지와 간격 변경을 확인합니다. 간격이 바뀌면 기존 회차 기준 시각에서 다음 예약을 다시 계산하여 표시합니다.

숫자 옵션을 편집하다 잠시 빈칸이 되거나 범위를 벗어나도 전체 설정 저장이 실패하지 않도록 마지막 유효값을 유지합니다. 프롬프트와 다른 옵션의 저장, 종료 시 저장을 함께 막지 않습니다. `NaN`이나 무한대도 유효한 중복 임계값으로 저장하지 않습니다.

## 7. 키워드 이력과 보존 기간

글 주제와 원래 검색어를 별도로 기록합니다. 발행 확인 후에는 실제 글 주제, `source_topic`, 사용한 연관 검색어를 소비 키로 등록하고 DB에서 제거합니다. 다음 수집에서도 같은 소비 키를 제외합니다.

DB의 문자열 목록을 매번 새 기록으로 만들던 처리를 제거했습니다. `keyword_db_records`를 기준으로 기존 `first_seen`과 `last_seen`을 보존하고 실제 재관측한 키워드의 `last_seen`만 갱신합니다.

병합과 저장 시 30일 보존 기간과 500개 상한을 적용합니다. 상한을 넘으면 최초 삽입 순서가 아니라 최근 관측 시각을 기준으로 남깁니다. 앱을 종료하지 않고 오래 켜 두었어도 만료 자료가 정리되도록 합니다.

## 9. 검증 전략과 마감 항목

### 자동 검증

- 새 글은 최신 프롬프트·역할·모델을 사용하고, 미완료 글은 저장된 설정을 유지하는지 확인합니다.
- 대기 중 간격을 늘이거나 줄였을 때 예약이 갱신되고 중지 후 다음 회차가 실행되지 않는지 확인합니다.
- 빈 숫자 입력과 잘못된 값이 프롬프트 저장과 종료를 막지 않는지 확인합니다.
- 자연스러운 구성에서 구역별 650자와 밀도 하한을 강제하지 않으면서 전체 길이·8개 구역·공개 금지 표현 검사가 유지되는지 확인합니다.
- 중복 제목 수정 후 같은 주제로 이어가며 준비 완료 캐시를 그대로 재거절하지 않는지 확인합니다.
- 이미지 한 위치가 실패해도 다른 승인본을 재생성하지 않고, 재실행 후에도 추가 생성 한도가 유지되는지 확인합니다.
- Google 기본 요청 수와 최대 수, 최종 이미지 16장 상한, 생성 이미지 부족분 보충 규칙을 확인합니다.
- Google 사진의 원문 사용 조건과 원본 문자 검수를 통과하지 않으면 설명 추가·발행 경로로 넘어가지 않는지 확인합니다.
- 캡션 길이·한글·URL·줄바꿈 검사, 상단 별도 영역, 원사진 픽셀 보존, EXIF 방향·원본 보존을 확인합니다.
- 최종 캡션 OCR 결과가 문구와 다르거나 다른 문자가 있으면 승인되지 않는지 확인합니다.
- 최종 제출 전 오류는 같은 원고로 복구하고, 성공 영수증이 있으면 최종 발행 버튼을 다시 누르지 않는지 확인합니다.
- 게시 내용 확인 실패가 게시 성공을 취소하거나 산출물을 삭제하지 않는지 확인합니다.
- 원검색어와 사용 연관어가 소비되고 재수집되지 않으며, 다른 키워드의 관측 시각은 유지되는지 확인합니다.

### 통합 연동 확인

CLI 영어 검색어 생성 → 영어 원문 확인 → 캡처 호출의 연결을 완료했습니다. `plan_google_image_search`는 저장된 단계별 CLI·모델을 사용해 영어 3~8단어를 만들고, `capture_google_reference_candidates(..., english_only=True, reuse_only=True)`가 영어 검색 설정과 실제 원문 언어·사용 조건을 확인합니다. 원고와 캡션은 한국어로 유지합니다. 현재 지원하는 권리 확인 원문은 Wikimedia Commons의 개별 파일 페이지이며, 그 밖의 사이트 사진은 자동 채택하지 않습니다.

실제 이미지 사본 생성부터 준비 결과, 발행 전 검사까지 연결한 오프라인 통합 테스트에서 생성 사진 6장과 한글 캡션을 추가한 참고사진 10장, 총 16장이 통과했습니다. 이 과정에서 발행 자료 최상위의 `cover_headline` 누락을 발견해 보존하도록 수정했습니다. 이전 버전 미완료 작업은 원고만 있는 `article.json` 대신 이미지·검수까지 포함한 `manifest.json`을 읽고, 제출 불확실 상태는 영수증 파일이 없어져도 다시 발행 가능한 상태로 바꾸지 않습니다.

화면에서는 저장한 프롬프트·모델·Google 수량·이미지 재생성·글 구성 모드가 재실행 뒤 복원되는지, 모든 탭의 하단 진행 창과 예약 안내가 올바른지 확인합니다. 이후 빌드 결과와 실행 파일 경로를 기록합니다.

실제 게시 검증을 수행할 경우에는 최종 게시 URL, 선택한 완료 동작, 게시 본문·사진 확인 결과, 영수증 재사용 여부를 함께 기록합니다. 임시저장이나 테스트 대역을 이용한 검증 결과를 실제 발행 성공으로 기재하지 않습니다.
